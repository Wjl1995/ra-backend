## 二、SQLite 过渡期方案设计

### 2.1 核心思路

原方案要求 PostgreSQL + Redis + 独立 worker + 对象存储，当前只有 SQLite 单文件 + 同步处理。直接跳跃成本太高，采用**过渡期方案**：

```
过渡期（MVP 验证）                      生产期（验证通过后迁移）
┌──────────────────────┐               ┌──────────────────────┐
│  SQLite (WAL 模式)    │  ──迁移──→   │  PostgreSQL           │
│  本地文件系统          │  ──迁移──→   │  MinIO / COS           │
│  SQLite 任务队列       │  ──迁移──→   │  Redis + RQ            │
│  API 内 BackgroundTask │  ──迁移──→   │  独立 Worker 进程       │
│  ChromaDB (本地持久化) │  ──保留──→   │  ChromaDB / pgvector   │
└──────────────────────┘               └──────────────────────┘
```

**关键原则**：所有基础设施组件通过抽象接口访问，过渡期用 SQLite/本地实现，生产期切换实现类即可，业务代码不动。

### 2.2 SQLite 并发策略

| 问题 | 方案 |
| --- | --- |
| API 与 Worker 同时写 | SQLite WAL 模式，读不阻塞写，写不阻塞读 |
| Worker 任务领取竞争 | `BEGIN IMMEDIATE` + `UPDATE ... WHERE status='queued' RETURNING` 模拟 `SELECT FOR UPDATE SKIP LOCKED` |
| 写锁超时 | 设置 `busy_timeout=5000ms`，自动重试 |
| 长事务阻塞 | 每个任务步骤独立提交，不持有长事务 |
| 单写者瓶颈 | 过渡期只有 1 个 worker，不构成瓶颈；多 worker 是生产期的事 |

### 2.5 聊天联网同步/异步策略

过渡期不启动独立 worker 进程，对话联网快车道在 API 进程内完成：

```
用户发送消息 (web_mode=auto)
  │
  ├─ 同步阶段（预算 15 秒）
  │   ├─ 本地检索
  │   ├─ WebNeedDetector 判断
  │   ├─ 如果需要联网：WebSearch → Fetch Top 3 → Normalize
  │   ├─ 构造上下文 → LLM 回答
  │   └─ 返回完整回答 + citations
  │
  └─ 异步阶段（BackgroundTasks）
      └─ 知识沉淀：将引用的网页写入用户个人知识库
         ├─ 保存 SourceSnapshot
         ├─ 创建 Document + DocumentVersion
         ├─ 调用 Organizer 生成 KnowledgeCard
         └─ 写入 ChromaDB 索引
```

- 15 秒内完成 → 返回 `status=completed` + 完整回答
- 超时 → 返回 `status=thinking` + `thinking_id`，前端轮询
- 知识沉淀始终异步，不影响回答延迟

### 2.6 Worker 设计（过渡期：进程内线程池）

深度采集需要较长耗时，不能在 API 请求内完成。过渡期用**后台线程**而非独立进程：

```python
# 过渡期：API 进程内启动 1 个后台线程作为 worker
# 生产期：切换为独立进程 + Redis 队列
class InProcessWorker:
    """在 API 进程内运行的后台 worker 线程"""
    def start(self):
        self._thread = threading.Thread(target=self._loop, daemon=True)
        self._thread.start()
    
    def _loop(self):
        while not self._stop.is_set():
            job = self.queue.claim(worker_id="in-process", job_types=["crawl", "organize", "ingest"])
            if job:
                self.dispatcher.handle(job)
            else:
                time.sleep(2)  # 空闲时降低轮询频率
```

## 七、风险与缓解

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| SQLite 写锁竞争 | API 与 Worker 线程同时写 | WAL 模式 + busy_timeout + 短事务 |
| 搜索 API 费用 | 影响联网回答可用性 | 用户级配额 + 缓存搜索结果 + 降级本地回答 |
| 浏览器渲染资源 | 进程内 Crawl4AI 占内存 | 限制并发 context 数 + 单任务预算 + 超时强杀 |
| LLM 整理成本 | 每页一次 LLM 调用 | 仅质量门禁通过的页面整理 + 批量处理 |
| BackgroundTasks 丢失 | API 进程崩溃时未完成的沉淀丢失 | 任务状态持久化到 DB，启动时恢复未完成任务 |
| 小程序审核 | 联网功能触发审核风险 | 文案避免"搜索引擎"，描述为"知识增强" |
| robots 合规 | 抓取被禁站点 | 默认尊重 robots + 审计日志 |

## 八、迁移到生产基础设施的检查清单

当 MVP 验证通过，满足以下任一条件时启动 Phase 8 迁移：

- [ ] SQLite 写入延迟超过 100ms（并发瓶颈）
- [ ] 需要 2 个以上 Worker 并行处理
- [ ] 数据量超过 1GB 或 10 万条文档
- [ ] 需要跨机器部署
- [ ] 需要 SSE 实时推送（Redis Pub/Sub）

迁移步骤验证清单：

- [ ] PostgreSQL 容器启动，pgvector 扩展安装
- [ ] Alembic migration 在 PostgreSQL 上执行通过
- [ ] SQLite → PostgreSQL 数据迁移脚本验证通过
- [ ] Redis 容器启动，RedisTaskQueue 单元测试通过
- [ ] 独立 Worker 进程启动，可领取 Redis 队列任务
- [ ] API 切换到 PostgreSQL，现有功能回归测试通过
- [ ] 对象存储切换到 MinIO，快照读写验证通过
- [ ] 压力测试：并发 10 用户对话 + 2 个 crawl job，无锁超时

## 九、建议的即时行动

1. **确认搜索 API 选型** — Tavily（1000 次/月免费）或 Serper（2500 次/月免费），注册获取 API Key
2. **安装新依赖** — `pip install httpx beautifulsoup4 lxml crawl4ai simhash alembic`
3. **验证 Crawl4AI 可用** — 跑一个示例页面确认浏览器渲染环境正常
4. **初始化 Alembic** — `alembic init alembic` → 配置 `alembic.ini` → 生成 baseline
5. **启用 SQLite WAL** — 在 `database.py` 的 engine 连接事件中执行 `PRAGMA journal_mode=WAL`
6. **准备测试样本集** — 20 个真实问题（覆盖时效/知识/本地/失败）+ 5-10 个站点（静态/JS/列表详情/sitemap）
