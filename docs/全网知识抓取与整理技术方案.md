# 全网知识抓取与整理技术方案

> 状态：设计稿，供 ra-backend、ra-miniapp、ra-webapp 联合评审。
>
> 范围：以“对话中自动联网回答并沉淀到个人知识库”为第一目标，同时覆盖用户主动 URL 抓取、站点深度采集和后续规模化演进。

## 1. 结论先行

本需求不应被实现成一个“给 URL，调用爬虫，直接塞进 Chroma”的接口，也不应把联网能力单独做成一个与聊天无关的爬虫后台。真正要解决的问题是：

1. 在合法、可控、可复现的前提下获取网页事实。
2. 保留原始证据，允许追溯、重跑、纠错和删除。
3. 将网页转换为稳定的、可检索的知识对象，而不是只保存一段摘要。
4. 让长耗时任务不占用 FastAPI 请求进程，并能恢复、重试、取消。
5. 让前端能看到任务进度、失败原因、来源和知识整理结果。
6. 用户在小程序或网页发起对话时，系统能自动判断是否需要联网，并将实际使用的网络来源沉淀为该用户的个人知识。

推荐的首版目标是“对话联网快车道 + 受控深度采集”：

- 对话联网快车道：根据用户问题搜索网页，抓取少量高相关页面，尽快完成当前回答，并异步沉淀实际引用来源。
- 受控深度采集：用户提交 URL、站点首页、sitemap 或 RSS，在明确的页面数、深度、域名、频率和时间预算内批量抓取。

所谓“全网”只能是可调度的 URL frontier，不能承诺无边界扫描互联网。

推荐总体形态：

~~~mermaid
flowchart LR
    A[ra-miniapp / ra-webapp] --> B[FastAPI Control Plane]
    B --> C[Chat Turn Orchestrator]
    C --> D[Local Knowledge Retrieval]
    C --> E[Web Need Detector]
    E --> F[Web Search Provider]
    F --> G[Fetch Worker]
    B --> H[(PostgreSQL)]
    B --> I[(Redis Queue)]
    I --> G
    G --> J[Source Adapters]
    J --> K[Raw Object Storage]
    G --> L[Normalize and Extract]
    L --> M[Knowledge Organizer]
    M --> H
    M --> N[Personal Knowledge Ingest]
    N --> O[Vector Index]
    H --> P[Answer with Citations]
    O --> P
~~~

第一期推荐：PostgreSQL + Redis + 独立 Python worker + 本地文件存储或 MinIO。现有 SQLite 仅适合开发和单进程验证，不适合作为并发抓取任务的生产状态库。即时聊天回答和异步知识整理可以共享 worker 基础设施，但不能共享无用户隔离的全局知识对象。

### 1.1 产品验收标准

用户在小程序或网页发送一个需要实时信息的问题时，系统必须能够：

1. 自动判断本地个人知识是否足够；不足或问题具有时效性时触发联网。
2. 通过 Web Search Provider 发现候选页面，而不是只等待用户提供 URL。
3. 抓取和清洗高相关页面，在回答中给出可点击、可追溯的网页引用。
4. 将实际参与回答的来源异步写入当前用户的个人知识库，并保留原始快照、版本和证据。
5. 后续相似问题可以优先命中已经沉淀的个人知识；来源更新后可以产生新版本。
6. 网络搜索失败时明确告知用户，并保留本地知识回答或降级回答，不伪造联网结果。

## 2. 第一性原理

### 2.1 知识系统的最小闭环

对话知识系统的基本闭环不是“请求网页”，而是：

~~~
用户问题 -> 本地检索 -> 是否需要联网 -> 搜索发现 -> 访问授权判断
-> 获取快照 -> 内容抽取 -> 当前回答与引用 -> 去重与版本化
-> 个人知识整理 -> 检索发布 -> 可追溯反馈
~~~

任何一个环节缺失都会导致系统难以运营：没有快照就无法复核，没有版本就无法处理更新，没有去重就会污染检索，没有质量状态就会把低质量摘要当成事实。

### 2.2 四个不可妥协的不变量

| 不变量 | 设计要求 |
| --- | --- |
| 证据优先 | 生成的摘要、标签、实体和问答必须引用来源页面与片段；原文永不被生成内容覆盖。 |
| 任务可恢复 | API 返回任务 ID；任务状态持久化；worker 可重启；重复投递不会产生重复文档。 |
| 用户隔离 | source、crawl_job、document、knowledge_card 均带 owner_id，所有查询按当前用户过滤。 |
| 边界可证明 | 每个任务有最大 URL 数、最大深度、最大字节数、超时、并发度、允许域名和 robots 策略。 |

### 2.3 “抓取”和“整理”必须分离

抓取回答“网页当前是什么”；整理回答“如何把内容组织成可用知识”。两者使用不同的失败重试和质量标准：

- 网络超时、429、浏览器崩溃属于采集失败，可重试。
- 内容为空、正文比例过低、来源疑似软 404 属于内容质量失败，应记录证据并进入人工处理。
- LLM 输出不符合结构、引用缺失或置信度过低属于整理失败，不应删除已保存的原文。

## 3. 现状与改造边界

### 3.1 现有能力

ra-backend 当前已经有：

- FastAPI、JWT Bearer 鉴权和按用户隔离的 Document。
- knowledge/ 中的 Markdown、PDF、DOCX、PPTX、XLSX、TXT、JSON 解析和分块逻辑。
- Document / DocumentChunk 表，以及基于 Chroma 和文本匹配的检索路径。
- 文档上传接口 POST /api/v1/documents，但上传请求内同步完成解析。
- ra-miniapp 和 ra-webapp 均已封装文档列表、详情、上传和搜索调用。

### 3.2 当前限制

- 默认 SQLite，没有适合并发 worker 的任务领取、租约和锁语义。
- 没有持久化的通用 job/event 表；现有异步思路不能作为采集系统的状态源。
- Document 的来源字段只有本地 source_path，无法表达 canonical URL、抓取时间、HTTP 响应、版本和证据。
- Chroma 可以继续承载第一期向量索引，但不应成为事实数据源。
- 当前 /documents 与 /search 是用户文档接口，不能直接扩展为“全网公共知识”接口而破坏权限边界。
- 当前聊天流程没有 Web Search Provider、联网触发策略或聊天来源沉淀任务。
- Agent Runtime 的全局 AgentMemory/KnowledgeStore 和 save_experience 不能直接作为个人知识库写入通道；所有写入必须经过带 user_id 的后端服务。

### 3.3 改造原则

1. 保留现有 /api/v1/documents、/api/v1/search 和聊天接口，保证旧前端继续可用。
2. 新能力挂在 /api/v1/knowledge 下，避免把采集任务伪装成同步文档上传。
3. 新采集文档最终映射到现有 Document / DocumentChunk，增加来源、版本、质量和任务关联。
4. 新接口先按用户私有知识库设计；公共知识库、团队协作和管理员审核作为后续权限模型扩展。

## 4. 目标架构

### 4.1 控制面与执行面

控制面（FastAPI）负责：

- 鉴权、参数校验、SSRF 防护和额度校验。
- 创建 source、crawl job、取消任务、查询状态。
- 只写数据库和队列，不执行网页抓取和浏览器操作。
- 返回稳定的资源模型，供两个前端使用。

聊天编排面（Chat Turn Orchestrator）负责：

- 根据本地召回结果、问题时效性和用户的 web_mode 判断是否联网。
- 生成搜索查询和搜索计划，限制搜索次数、页面数、预算和超时。
- 将本地知识和网络证据统一交给回答模型，生成带 citation_id 的回答。
- 创建知识沉淀任务，不在聊天请求内同步完成全量整理。

执行面（worker）负责：

- 领取任务并维护租约。
- URL 规范化、robots 判断、限速、重试和 frontier 管理。
- 按访问策略选择 HTTP、JS 浏览器或外部 Reader。
- 保存原始响应和规范化内容。
- 执行去重、质量评分、知识整理、切片和索引。

### 4.2 两条业务通道

#### 对话联网快车道

~~~text
Chat Message
-> Local Retrieval
-> Web Need Detector
-> Web Search Provider
-> Fetch Top N Pages
-> Normalize and Quality Gate
-> Answer Synthesizer
-> Citation Builder
-> Async Personal Knowledge Ingest
~~~

快车道只抓取回答所需的少量页面，目标是可控的交互延迟。它的成功标准是“当前回答正确且有来源”，不是一次性建立完整站点索引。

#### 深度采集通道

~~~text
Source / URL / Sitemap / RSS
-> Frontier
-> Multi-page Fetch
-> Snapshot and Version
-> Organize
-> Batch Index
~~~

深度通道适合用户主动导入一个网站或长期订阅来源，使用现有 crawl job 状态机。两条通道共享快照、整理、去重和索引能力，但 job 的 origin、预算和交互协议不同。

### 4.3 任务状态机

~~~mermaid
stateDiagram-v2
    [*] --> queued
    queued --> running
    running --> cancelling
    cancelling --> cancelled
    running --> succeeded
    running --> partially_succeeded
    running --> failed
    queued --> cancelled
    failed --> queued: retry
    partially_succeeded --> queued: retry_failed
~~~

每个 job 还应有计数器：discovered_count、scheduled_count、fetched_count、accepted_count、organized_count、failed_count、skipped_count。进度百分比不能只由时间估算；当总 URL 数未知时前端显示阶段和计数，不显示虚假的精确百分比。

### 4.4 内容数据流

~~~mermaid
flowchart TD
    A[Seed URL / sitemap / RSS] --> B[Canonicalize URL]
    B --> C{Allowed?}
    C -- no --> X[skip with reason]
    C -- yes --> D[Fetch adapter]
    D --> E[Raw response snapshot]
    E --> F[HTML to Markdown / structured text]
    F --> G[Quality gate]
    G -- reject --> Y[record quality failure]
    G -- accept --> H[URL and content dedup]
    H --> I[Document version]
    I --> J[LLM / deterministic organizer]
    J --> K[Knowledge card and evidence]
    K --> L[Chunks and index]
~~~

## 5. 抓取策略与组件选择

### 5.1 Web Search Provider

网页抓取和网页搜索是两个不同能力。Jina Reader、Crawl4AI、Scrapling、Camoufox 负责访问或抽取页面，不能替代搜索引擎发现。

统一搜索接口：

~~~python
class WebSearchProvider(Protocol):
    name: str

    async def search(self, request: SearchRequest) -> SearchResult:
        """返回候选 URL、标题、摘要、发布时间、排名和 provider metadata。"""
~~~

SearchRequest 至少包括 query、language、region、freshness、top_k、safe_search 和 user_id。SearchResult 必须保留 provider、query、requested_at、result_rank 和原始 URL。

第一期建议接入一个合规的搜索 API，封装成可替换 provider；不得通过抓取搜索引擎结果页作为默认方案。搜索 provider 只负责发现候选 URL，正文必须经过受控 fetch adapter 获取和校验。

Web Need Detector 的判定优先级：

1. 用户显式要求联网、搜索、最新、今天、当前、实时或给出 URL 时，强制联网。
2. 问题涉及当前时间、价格、政策、版本、新闻、排名或快速变化事实时，默认联网。
3. 本地个人知识高置信命中且问题没有时效性时，可以不联网。
4. 模型不得仅凭“自己觉得不知道”无限触发搜索；必须受搜索次数和预算限制。

### 5.2 适配器接口

组件不应直接散落在业务 API 中，而应被封装为统一适配器：

~~~python
class FetchAdapter(Protocol):
    name: str

    async def fetch(self, request: FetchRequest) -> FetchResult:
        """返回原始响应、规范化候选文本和可审计的 fetch metadata。"""
~~~

FetchRequest 至少包括 URL、超时、最大响应字节、渲染模式、headers、代理策略、robots 结果和任务策略。FetchResult 至少包括最终 URL、状态码、content-type、响应头摘要、正文、抓取耗时、重定向链、错误码和适配器名称。

### 5.3 推荐的分层策略

| 层级 | 适用内容 | 首选实现 | 是否默认启用 |
| --- | --- | --- | --- |
| L0 | 静态 HTML、JSON、XML、RSS、sitemap | httpx/标准 HTML 解析器 + 自有清洗器 | 是 |
| L1 | 文档化网站、需要稳定正文抽取的页面 | Jina Reader 作为可选外部 Reader | 否，按租户/任务配置 |
| L2 | 需要执行 JavaScript 的页面 | Crawl4AI worker | 是，但只对命中 JS 策略的 URL 启用 |
| L3 | 复杂选择器、反爬导致普通请求失败的页面 | Scrapling 适配器 | 否，按站点策略启用 |
| L4 | 必须使用真实浏览器行为的高难页面 | Camoufox 独立浏览器池 | 否，人工批准或明确站点策略后启用 |

### 5.4 对建议组件的判断

Jina Reader：适合作为“正文抽取服务”或快速验证路径，不适合作为唯一事实来源。外部依赖会引入可用性、隐私、配额、成本和结果漂移问题；必须保留原始 URL、请求时间、Reader 版本/响应摘要，并支持关闭。

Crawl4AI：适合独立 worker 中的异步浏览器渲染、Markdown 输出和页面截图/HTML 证据保存。浏览器启动成本高，应使用按域名复用的 browser context、并发上限和单任务预算；不能在 FastAPI 进程内启动浏览器。

Scrapling：适合需要更强 CSS/XPath 选择器、请求会话和站点适配的场景。它应作为可插拔的站点 adapter，而不是整个系统的调度器或数据模型。

Camoufox：是高成本的最后一层。它不能被当作“绕过所有限制”的默认方案；应遵守站点条款、robots、法律和用户授权。浏览器池需要单独的资源限额、隔离、审计和人工开关。

因此第一期不建议四者同时作为强依赖。先实现 L0 + Crawl4AI，保留 Jina Reader 的 adapter 接口；Scrapling 和 Camoufox 在真实站点样本证明必要后再启用。

### 5.5 URL frontier 规则

每个 URL 在入队前执行：

1. 只允许 http 和 https，拒绝 file、ftp、data、本地回环和云元数据地址。
2. DNS 解析后再次检查 IP，防止域名解析到私网、环回、链路本地或保留地址。
3. 做 URL canonicalization：去掉默认端口、fragment、追踪参数，规范化 host、路径和百分号编码。
4. 校验允许域名、最大深度、路径前缀、文件扩展名、query 参数和每域名页面预算。
5. robots 作为默认门禁；若策略为人工批准，记录批准人、时间和理由。
6. 依据 ETag、Last-Modified 做条件请求；对 429 和 5xx 使用指数退避并尊重 Retry-After。

## 6. 知识整理设计

### 6.1 四层数据模型

| 层 | 作用 | 是否可被生成内容覆盖 |
| --- | --- | --- |
| SourceSnapshot | 原始 HTTP/浏览器响应、HTML/JSON、截图、抓取元数据 | 否，追加版本 |
| NormalizedDocument | 清洗后的 Markdown/结构化文本、标题树、语言、质量评分 | 否，按版本追加 |
| KnowledgeCard | 摘要、关键事实、主题、实体、问答、关系 | 可重算，但保留版本和模型信息 |
| RetrievalChunk | 面向检索的块、embedding、引用位置 | 可重建 |

### 6.2 整理流水线

1. 规范化：去导航、页脚、重复菜单、脚本和样式；保留标题层级、列表、表格、代码和链接。
2. 质量门禁：正文字符数、正文/HTML 比例、语言识别、重复率、软 404、发布时间和 canonical URL。
3. 确定性元数据：标题、作者、发布日期、canonical URL、语言、站点、内容 hash、抓取时间。
4. 模型增强：摘要、主题、关键词、实体、关键事实、FAQ 和相关主题。输出必须通过 JSON Schema 校验。
5. 证据绑定：每个关键事实关联 evidence[]，包含 document version、chunk id、原文区间或引用文本。
6. 去重合并：URL 去重、内容 hash 去重、SimHash/MinHash 近似去重；相似页面保留来源列表，不静默丢弃证据。
7. 发布判定：自动发布仅适用于质量分、引用完整性和安全检查均达标的内容；否则为 review_required。

### 6.3 LLM 的边界

LLM 用于压缩、分类和组织，不用于判断“网页内容是否真实”。对于日期、数字、政策、价格、代码和法律条款等高风险内容：

- 原文值和模型推断值分开存储。
- 返回答案时优先展示来源时间和原文证据。
- 低置信度、互相冲突或缺少引用的事实进入人工审核。
- 模型、提示版本和输入文档版本都写入 organizer_run。

### 6.4 对话联网结果的个人沉淀策略

默认策略为 knowledge_mode=auto：

- 只保存实际参与最终回答的网页来源，不保存搜索结果中未使用的页面。
- 保存对象为当前用户私有文档，带 source_type=web_search 和 origin_message_id。
- 原始快照和规范化文档先落库；摘要、主题、事实和 FAQ 在异步任务中生成。
- 知识整理失败不影响当前回答，失败状态可通过任务接口重试。
- 新文档默认进入当前用户可检索范围，但高风险内容或引用不完整时进入 review_required。
- 用户可以通过 knowledge_mode=off 关闭沉淀，或对已保存来源执行删除。

个人知识库写入必须遵守：

1. 所有 Document、DocumentVersion、KnowledgeCard、RetrievalChunk 均绑定 user_id。
2. Agent/MCP 不得直接调用全局 ChromaStore 或 MemoryStore 写入；只能调用 PersonalKnowledgeService。
3. PersonalKnowledgeService 在数据库事务中校验 user_id、来源归属、会话归属和幂等键。
4. 向量索引中的 metadata 至少包括 user_id、document_id、document_version_id、source_type 和 published 状态。

### 6.5 引用模型

当前回答的引用不应只包含 document_id。统一 Citation 至少包括：

~~~json
{
  "citation_id": "web_1",
  "ref_type": "web",
  "document_id": 301,
  "document_version_id": 3011,
  "title": "页面标题",
  "url": "https://example.com/article",
  "canonical_url": "https://example.com/article",
  "quote": "用于支撑回答的原文片段",
  "source_domain": "example.com",
  "published_at": "2026-07-27T08:00:00Z",
  "fetched_at": "2026-07-28T10:00:00Z"
}
~~~

### 6.6 建议的知识卡片结构

~~~json
{
  "title": "页面主题",
  "summary": "可读摘要",
  "topics": ["topic-a", "topic-b"],
  "entities": [{"name": "Entity", "type": "product"}],
  "facts": [
    {
      "statement": "一个可以被单独检索的事实",
      "confidence": 0.87,
      "evidence": [{"document_version_id": 301, "chunk_id": 9001, "quote": "原文引用"}]
    }
  ],
  "faq": [{"question": "用户可能问什么？", "answer": "基于证据的回答"}],
  "source": {"url": "https://example.com/page", "fetched_at": "2026-07-26T10:00:00Z"}
}
~~~

## 7. 数据库与存储

### 7.1 新增核心表

建议使用 Alembic 迁移，不继续在 startup 中堆叠手写 ALTER TABLE。

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| knowledge_sources | id、user_id、name、seed_type、seed_url、allowed_domains、policy_json、status | 一个可复用的抓取来源配置 |
| crawl_jobs | id、user_id、source_id、status、options_json、counters_json、idempotency_key、started_at、finished_at、error_code | 一次抓取运行 |
| crawl_pages | id、job_id、url、canonical_url、depth、status、adapter、http_status、content_hash、error_code | frontier 和页面级结果 |
| source_snapshots | id、crawl_page_id、final_url、storage_key、content_type、etag、fetched_at、sha256、size | 不可变原始快照 |
| document_versions | id、document_id、snapshot_id、version_no、normalized_storage_key、quality_score、language、published_at、content_hash | 文档内容版本 |
| knowledge_cards | id、document_version_id、status、payload_json、model、prompt_version、confidence | 结构化整理结果 |
| knowledge_evidence | id、knowledge_card_id、document_version_id、chunk_id、quote、start_offset、end_offset | 知识事实的证据绑定 |
| job_events | id、job_id、seq、type、payload_json、created_at | 前端进度、诊断和 SSE 的统一事件源 |
| web_search_runs | id、user_id、session_id、message_id、query、provider、status、results_json、created_at | 一次对话联网搜索 |
| chat_turn_sources | id、user_id、session_id、message_id、web_search_run_id、document_version_id、citation_id | 回答与网页来源的绑定 |
| knowledge_ingest_jobs | id、user_id、origin、message_id、status、document_ids、error_code | 对话来源转个人知识的异步任务 |

现有 documents 增加或关联：source_type、canonical_url、source_snapshot_id、current_version_id、quality_status、last_fetched_at。document_chunks 增加 document_version_id、chunk_index、content_hash 和可选的 locator_json。

新增字段约束：

- Message 或独立 ChatTurn 需要记录 web_mode、knowledge_mode、web_search_run_id、knowledge_ingest_job_id 和最终引用 JSON。
- crawl_jobs 增加 origin=manual_crawl|chat_search|scheduled_refresh，chat_search 必须关联 message_id。
- 对话自动保存产生的 Document.user_id 必须非空；禁止写入公共或全局 collection。

### 7.2 存储分工

- PostgreSQL：任务状态、权限、来源、页面索引、文档元数据、知识卡片和事件。
- 对象存储：原始 HTML/JSON、Markdown、截图、PDF 等大对象。生产使用 S3/MinIO；开发可用本地目录。
- Chroma：第一期继续作为向量检索索引，使用 document_version_id 和 user_id 元数据过滤。
- 后续：当数据量、过滤条件和多租户需求增长时，评估 PostgreSQL + pgvector，减少双存储一致性复杂度。

### 7.3 幂等与一致性

- POST /crawl-jobs 支持 Idempotency-Key，同一用户同一 key 在有效期内返回原 job。
- canonical_url + content_hash 建立唯一/半唯一约束，避免重复版本。
- 所有索引写入以 document_version 为单位；只有索引成功后才把版本标记为 searchable。
- worker 使用 lease_until 和 attempt；租约过期的页面可以被重新领取。
- 任务完成不等于所有页面成功，使用 succeeded 和 partially_succeeded 区分。

## 8. API 设计原则

完整契约见同目录的《全网知识抓取与整理 API 契约》。新接口统一前缀 /api/v1/knowledge：

~~~text
sources       可复用的来源配置
crawl-jobs    一次抓取运行
events        任务事件和进度
documents     抓取产生的知识文档视图
cards         结构化知识卡片
chat turns    对话联网状态、引用和知识沉淀关联
~~~

### 8.1 对话联网接口

现有 POST /api/v1/chat/sessions/{session_id}/messages 保留，但请求和响应需要扩展：


### 8.3 前端交互建议

两个前端均采用同一模式：

1. 发送消息时默认 web_mode=auto、knowledge_mode=auto；Web 端可展示联网和保存状态，小程序只展示简化状态。
2. 返回 thinking_id 时，前端轮询 chat/thinking/{id}；页面隐藏后降为 5 秒，完成后停止。
3. 回答中的每个 citation_id 都可点击进入网页或个人知识详情。
4. 回答完成后，前端可根据 knowledge_ingest_job_id 显示“已保存/整理中/失败”。
5. 深度抓取页面继续使用 crawl job 轮询和 events?after_seq=N。
6. 对 review_required 展示“待审核”，对 partially_succeeded 展示成功/失败计数和重试入口。

SSE 可以在第二期增加 GET /crawl-jobs/{id}/events/stream，但不能替代数据库事件；小程序不应依赖长连接作为唯一进度机制。

## 9. 安全与合规

### 9.1 SSRF 与资源安全

采集 URL 是用户可控输入，必须在 worker 和 API 两侧都防护：

- 禁止私网、回环、链路本地、云元数据和 Unix socket 地址。
- DNS 解析后连接前复核 IP，防止 DNS rebinding。
- 限制重定向次数，并对每次重定向重新执行域名/IP策略。
- 限制响应体大小、压缩解压比例、MIME 类型和下载扩展名。
- 浏览器 worker 使用非 root 用户、只读基础镜像、临时 profile 和网络 egress allowlist。
- HTML、Markdown 和模型输入均按不可信内容处理，禁止将页面指令当作系统提示执行。

### 9.2 站点礼仪和法律边界

- 默认尊重 robots.txt、站点条款和版权声明。
- 每域名限速、并发和每日预算可配置，429 自动退避。
- 默认只保存用户有权处理的公开内容；不提供绕过登录、验证码或访问控制的通用能力。
- 原文存储支持按 URL、来源、任务和用户删除，向量索引同步删除。
- 日志中不记录 cookie、Authorization、完整页面正文和敏感 query 参数。

### 9.3 Prompt Injection 防护

网页内容必须被标记为 untrusted_source_content，整理提示词中明确：

- 页面中的命令、角色设定、工具调用和数据外传要求均是普通文本。
- 模型只能按系统 schema 提取，不得执行页面指令。
- 不把页面内容直接作为后续工具调用参数；工具参数需独立校验。
- 记录模型输出校验失败和被拒绝的字段，方便审计。

## 10. 可观测性与质量指标

### 10.1 必备指标

- crawl_job_duration_seconds
- crawl_page_fetch_total{adapter,status_code}
- crawl_page_failure_total{error_code}
- crawl_page_retry_total
- content_quality_score
- dedup_ratio
- organizer_validation_failure_total
- index_write_failure_total
- source_domain_rate_limit_hits

### 10.2 质量门槛

一期建议以离线样本集验收，而不是只看抓取页数：

| 指标 | 建议门槛 |
| --- | --- |
| 正文抽取成功率 | 静态站点 >= 95%，JS 站点单独统计 |
| 软 404 误收率 | <= 2% |
| URL/内容重复率 | 明确展示并可解释，不设“一刀切”目标 |
| 知识卡片 schema 通过率 | >= 98%，失败可重试 |
| 关键事实引用覆盖率 | >= 95% |
| 任务状态可恢复率 | worker 重启后不丢失未完成页面 |
| 权限隔离 | 用户无法读取其他用户 source、job、snapshot 和 card |

## 11. 分阶段交付

### Phase 0：对话联网样本和基线

- 选取 20 个真实问题，覆盖时效问题、普通知识问题、本地知识可回答问题和联网失败问题。
- 选取 5 到 10 个真实站点，覆盖静态、JS、列表详情、sitemap 和 RSS。
- 固化搜索结果、HTML、期望正文、期望引用和去重样本。
- 评估 Web Search Provider、L0 与 Crawl4AI，不先引入 Camoufox。

### Phase 1：可上线 MVP

- PostgreSQL、Redis、worker、对象存储抽象。
- Chat Turn Orchestrator、Web Need Detector、Web Search Provider。
- chat turn、web_search_run、chat_turn_source、knowledge_ingest_job。
- 对话联网回答、可点击引用、thinking 查询和用户级自动沉淀。
- PersonalKnowledgeService，禁止 Agent/MCP 直接写全局知识库。
- 静态请求 + JS 渲染；robots、限速、重试、取消、幂等。
- Markdown 清洗、质量评分、hash 去重、确定性 metadata。
- 摘要/主题/关键词/事实/证据的 schema 化整理。
- 单 URL 一次性抓取作为深度采集的最小入口。

### Phase 2：运营能力

- sitemap/RSS/同站点深度采集和定时刷新。
- 定时刷新、增量抓取、ETag/Last-Modified。
- Jina Reader 和 Scrapling adapter。
- 人工审核、版本 diff、单页重试、批量发布和删除。
- SSE、后台任务筛选、站点级策略模板和成本统计。

### Phase 3：规模化和复杂站点

- Camoufox browser pool，仅用于经过批准的站点策略。
- 分布式 frontier、按域名调度、优先级和搜索发现。
- PostgreSQL + pgvector 或独立检索服务评估。
- 团队/公共知识库、角色权限、知识图谱和跨来源冲突检测。

## 12. 实施顺序

1. 先写迁移和领域模型，确认 ChatTurn、WebSearchRun、KnowledgeIngestJob 和所有 job 状态都由数据库表达。
2. 实现 PersonalKnowledgeService，先解决 user_id、来源归属、幂等和删除。
3. 把现有同步文档解析抽成可被 worker 调用的 pipeline。
4. 实现 Web Search Provider、Web Need Detector 和对话联网快车道。
5. 实现 L0 HTTP adapter、robots、URL 规范化、快照存储和幂等。
6. 接入 Crawl4AI 作为独立 adapter，增加浏览器资源限制。
7. 接入整理器、证据绑定、版本化和 Chroma 索引。
8. 按 API 契约实现两个前端的聊天联网状态、引用、知识库和深度采集页面。
9. 用样本集和故障注入验证联网失败、重复消息、取消、worker 重启、跨用户隔离和删除。

## 13. 不建议的方案

- 不建议在 FastAPI 请求函数里直接 await 整个爬取任务。
- 不建议把网页正文和摘要只存进一个 Document.summary 字段。
- 不建议让 Chroma 成为唯一事实存储。
- 不建议默认启用 Camoufox 或以“绕过反爬”为系统卖点。
- 不建议用进程内 BackgroundTasks 代替持久化队列。
- 不建议将未经引用的 LLM 事实直接标记为已发布知识。
- 不建议把“用户主动创建 crawl job”当作“聊天自动联网”能力的替代。
- 不建议让搜索结果直接进入全局 Chroma collection；所有个人沉淀都必须经过 PersonalKnowledgeService。
